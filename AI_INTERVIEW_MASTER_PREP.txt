Q8: Explain your database design.

   plan (FREE/PRO/ENTERPRISE enum).

- User → many OrganizationMembers (many-to-many through junction table)
- Organization → many OrganizationMembers
- Organization → many Interviews
- User → many Interviews (as creator)

I used onDelete: Cascade so deleting a User removes their memberships, and
deleting an Organization removes all its memberships and interviews."

KEYWORDS: CUID, indexing, composite unique constraint, junction table,

Q9: How does authentication work in your application?

ANSWER:
"I implemented JWT-based stateless authentication:

Registration:
1. User sends name, email, password to POST /api/auth/register
2. Service checks if email already exists (throws 409 if duplicate)
3. Password is hashed using bcrypt with 12 salt rounds
4. User record created in PostgreSQL via Prisma

Login:
1. User sends email, password to POST /api/auth/login
2. Service fetches user by email
3. bcrypt.compare() verifies password against stored hash
4. JWT signed with user.id as 'sub' claim, 7-day expiry
5. Token + user object returned to client

Frontend:
1. Token stored in localStorage
2. Axios request interceptor attaches 'Bearer <token>' header
3. Zustand store persists auth state with persist middleware
4. Response interceptor catches 401 → clears token → redirects to login

Protected Routes:
1. auth.middleware.ts extracts token from Authorization header
2. jwt.verify() validates signature and expiry
3. userId extracted from payload.sub and attached to req.userId
4. If invalid → throws AppError with 401 status"

KEYWORDS: stateless, bcrypt, salt rounds, JWT claims, sub, Bearer token,
          interceptors, middleware chain, 401 handling

Q10: How does the real-time coding room work?

ANSWER:
"The coding room uses Socket.IO for WebSocket communication and Monaco Editor
for the code editor:

Architecture:
- Server creates an HTTP server, then wraps it with Socket.IO with CORS config
- Client connects using socket.io-client with lazy initialization (singleton)

Room Flow:
1. User navigates to /room/[interviewId]
2. Socket connects and emits 'room:join' with roomId, userId, name
3. Server uses Socket.IO rooms (socket.join(roomId)) for room isolation
4. Server assigns a color to each user and tracks users in a Map<roomId, Map<socketId, RoomUser>>
5. Broadcasts 'room:users' to all clients in the room

Code Synchronization:
1. When user types in Monaco Editor, onChange fires
2. Client emits 'code:change' with roomId and code
3. Server broadcasts 'code:update' to OTHER users (socket.to() excludes sender)
4. Receiving client sets isRemoteChange flag to prevent echo loop
5. Same pattern for 'language:change' / 'language:update'

Cleanup:
- On 'disconnecting' event, server removes user from roomUsers Map
- Broadcasts updated user list to remaining users
- If room is empty, deletes the room entry from Map"

KEYWORDS: WebSocket, Socket.IO rooms, broadcasting, echo prevention, singleton,
          lazy initialization, Map data structure, room isolation

Q13: How does the background job processing work?

ANSWER:
"I use BullMQ with Redis for asynchronous job processing:

Why Background Jobs?
- Resume analysis takes 10-30 seconds (PDF parsing + AI call)
- Without background processing, the HTTP request would timeout
- Background processing makes the API non-blocking

Implementation:
1. Queue: 'resume-analysis' queue with default options:
   - 3 attempts per job
   - Exponential backoff (5 second base delay)
   - Keeps last 100 completed jobs, last 50 failed jobs

2. Producer (resume.controller.ts):
   - Generates a UUID as jobId
   - Stores initial status 'processing' in Redis cache
   - Adds job to queue with { jobId, resumeText }
   - Returns jobId to client immediately

3. Worker (resume.queue.ts):
   - Processes jobs from the queue
   - Calls analyzeResumeText() with Gemini
   - On success: stores { status: 'completed', data: feedback } in Redis
   - On failure: stores { status: 'failed', error: message } in Redis
   - Emits 'completed' and 'failed' events for logging

4. Status Polling:
   - Client polls GET /api/ai/resume/status/:jobId every 2 seconds
   - Returns current status from Redis cache
   - Frontend shows spinner until completed, then renders results"

KEYWORDS: BullMQ, producer-consumer, exponential backoff, non-blocking,
          UUID, polling, job lifecycle, retry mechanism

Q15: How do you handle scalability in your application?

ANSWER:
"Several design decisions support scalability:

1. Stateless Backend: JWT tokens mean no server-side sessions — any server
   instance can handle any request. Easy to horizontally scale.

2. Redis Caching: Reduces database load and AI API calls. Cache-aside pattern
   means the database is the source of truth.

3. Background Job Processing: BullMQ distributes work across workers. Can
   scale workers independently from the API server.

4. Database Indexing: Strategic indexes on User.email, Organization.slug,
   Interview.organizationId, and Interview.status for fast queries.

5. Docker Compose: Each service is independently scalable. Can add replicas
   of the server container behind a load balancer.

6. Socket.IO: Currently uses in-memory adapter. For horizontal scaling, I
   would switch to the Redis adapter (@socket.io/redis-adapter) so events
   are broadcast across all server instances.

7. Connection Pooling: Prisma handles PostgreSQL connection pooling
   automatically."

KEYWORDS: stateless, horizontal scaling, cache-aside, independent scaling,
          indexing, Redis adapter, connection pooling

Q19: How do you handle the real-time synchronization without conflicts?

ANSWER:
"In the current implementation, I use a 'last-write-wins' strategy for the
coding room:

Echo Prevention:
- When a user types, the client sends 'code:change' to the server
- Server broadcasts 'code:update' to OTHER users (socket.to() excludes sender)
- Receiving client sets isRemoteChange ref to true
- Monaco's onChange checks this flag — if true, it doesn't re-emit the change
- This prevents infinite echo loops

Current Limitations:
- No conflict resolution for simultaneous edits
- Last-write-wins means if two users edit the same line, one change is lost

How I Would Improve:
- Implement Operational Transformation (OT) or CRDT (Conflict-free Replicated
  Data Types)
- Use libraries like Yjs or Automerge for CRDT-based collaboration
- Or implement character-level OT similar to Google Docs
- Add cursor position broadcasting to show where other users are editing"

KEYWORDS: last-write-wins, echo prevention, socket.to(), ref flag,
          OT, CRDT, Yjs, cursor broadcasting

Q20: What is the Repository Pattern and why did you use it?

ANSWER:
"The Repository Pattern abstracts data access logic into a separate layer:

Structure:
Controller → Service → Repository → Database (Prisma)

Why:
1. Separation of Concerns: Controllers handle HTTP, Services handle business
   logic, Repositories handle database queries.
2. Testability: I can mock the repository in unit tests without needing a
   real database.
3. Flexibility: If I switch from Prisma to another ORM, I only change the
   repository layer.
4. Clean Code: Each file has a single responsibility.

Example in my code:
- InterviewController receives the request, extracts params
- InterviewService calls assertMember() for authorization, then calls repo
- InterviewRepository executes Prisma queries with includes and ordering

I also used Prisma's $transaction in the OrgRepository when creating an
organization and its first member atomically."

KEYWORDS: abstraction, separation of concerns, single responsibility,
          testability, flexibility, dependency injection, $transaction

Q25: What was the biggest challenge you faced?

ANSWER:
"The biggest challenge was implementing the real-time code synchronization
without creating echo loops.

Problem: When User A types, the change is sent to the server, which broadcasts
it to User B. But when User B's editor receives the remote update, Monaco's
onChange fires again, sending the same change back to the server — creating an
infinite loop.

Solution: I used a useRef (isRemoteChange) as a flag. When a remote code
update arrives via Socket.IO, I set isRemoteChange.current = true before
updating the state. In the onChange handler, I check this flag — if true, I
skip emitting the change and reset the flag. This breaks the loop.

Why useRef and not useState? Because useRef doesn't trigger a re-render, which
would cause performance issues in a real-time editor."

KEYWORDS: echo loop, useRef vs useState, re-render prevention, flag pattern,
          real-time debugging

────────────────────────────────────────────────────────────────────────────

Q26: What was the most interesting bug you solved?

ANSWER:
"The PDF text extraction was failing silently. Users would upload a resume
and get an error saying 'Could not extract text.'

Debugging: I discovered that pdfjs-dist was trying to use Web Workers in a
Node.js server environment, which doesn't have the Worker API.

Solution: I configured pdfjs-dist for server-side use:
- Set GlobalWorkerOptions.workerSrc to empty string (disable worker)
- Used the legacy build path (pdfjs-dist/legacy/build/pdf.js)
- Set useWorkerFetch: false, isEvalSupported: false, useSystemFonts: true

I also added a minimum text length check (50 characters) to detect scanned
PDFs (images) that don't have selectable text."

KEYWORDS: pdfjs-dist, Web Workers, server-side rendering, legacy build,
          silent failure, minimum validation, scanned PDFs

────────────────────────────────────────────────────────────────────────────

Q27: What trade-offs did you make in your design?

ANSWER:
"Several conscious trade-offs:

1. Last-write-wins vs CRDT: I chose simpler synchronization over conflict
   resolution. CRDT would be more correct but significantly more complex.
   Pragmatic choice for a project with mostly 1-2 concurrent editors.

2. Polling vs WebSocket for resume status: I used HTTP polling (every 2s)
   instead of pushing results via WebSocket. Polling is simpler to implement
   and debug, and resume analysis is infrequent.

3. localStorage vs HttpOnly cookies for JWT: localStorage is vulnerable to
   XSS but simpler to implement. HttpOnly cookies would be more secure but
   require server-side cookie handling and CSRF protection.

4. In-memory room tracking vs Redis: Socket.IO rooms use server-local memory.
   Works for single-server deployment but doesn't scale horizontally. Chose
   simplicity over immediate scalability.

5. Monorepo without tools: Used a simple folder structure instead of Nx or
   Turborepo. Avoided complexity since there are only two apps."

KEYWORDS: trade-offs, pragmatic decisions, complexity vs correctness,
          XSS vs CSRF, vertical vs horizontal, simplicity

────────────────────────────────────────────────────────────────────────────

Q28: What design decisions are you most proud of?

ANSWER:
"Three decisions I'm most proud of:

1. Making resume analysis asynchronous with BullMQ: Instead of blocking the
   API for 30 seconds, I return a jobId immediately and process in the
   background. This keeps the API responsive and allows retry on failure.
   It shows I understand production-grade patterns.

2. The generic cache module: Instead of Redis calls scattered throughout the
   code, I created getCache<T>, setCache, deleteCache functions with TypeScript
   generics. Type-safe, reusable, and gracefully handles Redis failures.

3. The error handling architecture: A custom AppError class + centralized
   error middleware means every error is handled consistently. No error leaks
   a stack trace. Every module just throws AppError and the middleware handles
   the rest."

KEYWORDS: asynchronous processing, generic cache, TypeScript generics,
          centralized error handling, production-grade patterns

SECTION 6 — INTERVIEWER TRAPS

────────────────────────────────────────────────────────────────────────────────
TRAP 1: "Is your application secure?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "Yes, I use JWT and bcrypt so it's secure."
WHY IT FAILS: Shows overconfidence, ignores real vulnerabilities

STRONG ANSWER: "I've implemented several security layers — bcrypt hashing,
JWT authentication, Helmet headers, CORS, and parameterized Prisma queries.
However, there are areas I'd improve: localStorage for JWT is vulnerable to
XSS (I'd switch to HttpOnly cookies), I don't have rate limiting yet, and
Socket.IO connections aren't authenticated. Security is layered, and I'm
aware of the gaps."

KEY: Acknowledge strengths AND weaknesses. Shows maturity.

────────────────────────────────────────────────────────────────────────────────
TRAP 2: "Can your app handle 1 million users?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "Yes, it's scalable because I use Redis."
WHY IT FAILS: Oversimplifies, doesn't show understanding

STRONG ANSWER: "Not in its current form, but the architecture supports scaling:
Stateless JWT allows horizontal scaling behind a load balancer. I'd need to
add Redis adapter for Socket.IO, database read replicas, rate limiting on AI
endpoints, and CDN for static assets. The BullMQ workers can scale independently.
I designed with scalability in mind, but production scaling requires additional
infrastructure."

KEY: "Not yet, but here's how I would" is better than "yes."

────────────────────────────────────────────────────────────────────────────────
TRAP 3: "Why didn't you use [X technology]?"
(e.g., GraphQL, MongoDB, Redux, Firebase, etc.)
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "I don't know that technology."
WHY IT FAILS: Shows limited awareness

STRONG ANSWER: "I considered it, but chose [my technology] because [specific
technical reason]. For example, I chose REST over GraphQL because my data
access patterns are predictable — each page needs specific endpoints. GraphQL
would add complexity without significant benefit for this use case. But for
a client with diverse data needs, GraphQL's query flexibility would be better."

KEY: Show you CHOSE deliberately, don't DEFEND defensively.

────────────────────────────────────────────────────────────────────────────────
TRAP 4: "What if two users edit the same line simultaneously?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "Socket.IO handles that automatically."
WHY IT FAILS: Shows lack of understanding of real-time conflicts

STRONG ANSWER: "Currently, I use last-write-wins — the second user's change
would overwrite the first. This is a known limitation. To properly handle
concurrent editing, I'd implement CRDTs (Conflict-free Replicated Data Types)
using a library like Yjs, which mathematically guarantees that concurrent
edits converge to the same state on all clients without conflicts."

KEY: Acknowledge the limitation, then show the better solution.

────────────────────────────────────────────────────────────────────────────────
TRAP 5: "You mentioned Docker. Can you explain how Docker networking works?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: Long pause... "Docker lets you run containers."
WHY IT FAILS: Claiming Docker knowledge but not knowing internals

STRONG ANSWER: "In Docker Compose, services are on the same default bridge
network. They can communicate using service names as hostnames — my server
connects to 'postgres:5432' and 'redis:6379' using service names, not
localhost. Docker resolves these names to container IPs internally. Port
mapping (5432:5432) exposes services to the host machine."

KEY: Know service discovery and port mapping if you mention Docker.

────────────────────────────────────────────────────────────────────────────────
TRAP 6: "What's the difference between authentication and authorization?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "They're the same thing."
WHY IT FAILS: Common beginner mistake

STRONG ANSWER: "Authentication verifies WHO you are (login, JWT verification).
Authorization verifies WHAT you can do (RBAC, assertMember checks). In my app,
the auth middleware handles authentication (verifying the JWT token). The
assertMember() function in services handles authorization (checking if the
user is a member of the organization they're trying to access)."

KEY: Give examples from your project for both.

────────────────────────────────────────────────────────────────────────────────
TRAP 7: "Tell me about a time you failed."
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "I don't usually fail."
WHY IT FAILS: Unrealistic, shows no self-awareness

STRONG ANSWER: "When building the resume analyzer, I initially tried to
process the PDF analysis synchronously in the API route. The request would
take 30+ seconds, and some requests would timeout. I realized I was blocking
the API for a long-running task. I refactored to use BullMQ background jobs,
which made the API non-blocking. The lesson was: always think about response
time and separate long tasks from the request cycle."

KEY: Show what went wrong, what you learned, and how you fixed it.

────────────────────────────────────────────────────────────────────────────────
TRAP 8: "What's the difference between SQL and NoSQL? Which is better?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "SQL is better because it has joins."
WHY IT FAILS: Shows bias without understanding trade-offs

STRONG ANSWER: "Neither is universally better — it depends on the use case.
SQL (PostgreSQL) is better for structured, relational data with ACID needs —
like my user-organization-interview relationships. NoSQL (MongoDB) is better
for flexible schemas, horizontal scaling, and document-shaped data — like a
content management system where each document might have different fields.
I chose SQL because my data is highly relational."

KEY: "It depends" + examples of when each is better.

────────────────────────────────────────────────────────────────────────────────
TRAP 9: "How do you test your code?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "I don't have tests yet."
WHY IT FAILS: Shows no testing mindset (even if true, don't say it bluntly)

STRONG ANSWER: "Currently, I test through manual testing and API testing with
tools like Postman. If I were to add automated tests, I'd use Jest for unit
tests on services and repositories (mocking Prisma), Supertest for API
integration tests, React Testing Library for component tests, and Playwright
for E2E tests. The Repository Pattern I use makes unit testing easy because
I can mock the repository layer."

KEY: Show you KNOW how to test even if you haven't fully implemented it.

────────────────────────────────────────────────────────────────────────────────
TRAP 10: "What makes you different from other candidates?"
────────────────────────────────────────────────────────────────────────────────

WEAK ANSWER: "I'm hardworking and a fast learner."
WHY IT FAILS: Generic, everyone says this

STRONG ANSWER: "I don't just build CRUD apps — I implement production-grade
patterns. My project uses background job processing with BullMQ, Redis caching
to reduce API costs, real-time WebSocket collaboration, AI integration with
proper error handling and fallbacks, and containerization with Docker. I think
about scalability, security trade-offs, and clean architecture from the start.
I built this project not just to learn, but to understand how real systems work."

KEY: Be specific about WHAT you do differently, backed by examples.

RED FLAGS IN YOUR RESPONSES — AVOID THESE
────────────────────────────────────────────────────────────────────────────────

❌ "I just used it because it was in a tutorial"
   → Say "I chose it because [technical reason]"

❌ "I don't know" (without follow-up)
   → Say "I'm not sure about that specific topic, but based on my
   understanding of [related concept], I think..."

❌ "My project has no limitations"
   → Always acknowledge trade-offs. It shows engineering maturity.

❌ "I used [technology] because everyone uses it"
   → Show you evaluated alternatives and made a deliberate choice.

❌ Memorizing answers word-for-word and sounding robotic
   → Understand the concepts, speak naturally, use your own words.

❌ Not asking for clarification when a question is vague
   → "Could you clarify — are you asking about X or Y?"

❌ Giving 5-minute answers to simple questions
   → Keep answers concise. 30-60 seconds max unless asked to go deeper.

❌ Not connecting answers back to your project
   → Always tie theoretical knowledge to your practical experience.

   developer on your team?"

which direction the interview goes. Steer it toward your strengths. Every
technology you mention will be tested — only mention what you're prepared for.
