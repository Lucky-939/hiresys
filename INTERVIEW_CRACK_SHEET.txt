Q1: What is HireSys?
A: HireSys is a production-grade, AI-powered interview and hiring
platform that I designed and built from the ground up as a full-stack
application. It provides organizations with a comprehensive suite of
interview management tools including real-time collaborative coding
rooms powered by Socket.IO and Monaco Editor, AI-driven question
generation and code review using Google Gemini, and an asynchronous
resume analyzer that calculates ATS compatibility scores through
background job processing with BullMQ and Redis. The platform
supports multi-tenant organization management where multiple
companies can operate independently with role-based access control
(RBAC), ensuring complete data isolation between tenants. The entire
system is containerized using Docker Compose for consistent
development and deployment environments.
KEYWORDS: AI-powered, real-time collaboration, multi-tenant
architecture, ATS scoring, asynchronous processing, RBAC,
containerized deployment, production-grade, full-stack application

Q2: What's the tech stack?
A: I chose a modern full-stack TypeScript monorepo architecture to
ensure end-to-end type safety across the entire application.
On the frontend, I use Next.js 16 with React 19 for server-side
rendering and file-based routing, Zustand for lightweight global
state management with persistence middleware, Axios with request
and response interceptors for API communication, Socket.IO client
for real-time WebSocket connections, and Monaco Editor (the same
editor engine that powers VS Code) for the collaborative coding
experience.
On the backend, I use Express 5 which provides built-in async
error handling, Prisma ORM for type-safe database queries and
automatic migration management on PostgreSQL, Redis as both a
caching layer for AI responses and as the message broker for
BullMQ job queues, Google Gemini AI for intelligent question
generation and resume analysis, JWT with bcrypt for stateless
authentication, Multer for secure file upload handling, and
Docker Compose for multi-service container orchestration.
KEYWORDS: full-stack TypeScript, monorepo architecture, end-to-end
type safety, server-side rendering, WebSocket, container
orchestration, message broker, stateless authentication, ORM

Q3: Explain the architecture.
A: The application follows a monorepo structure with two distinct
applications — a Next.js frontend and an Express backend — sharing
a common TypeScript foundation. The backend is designed around the
Repository Pattern, which enforces a strict separation of concerns
through four distinct layers: Routes define the API endpoints and
attach middleware, Controllers handle HTTP request/response parsing
and validation, Services encapsulate all business logic and
orchestration, and Repositories abstract away all database access
using Prisma ORM. This layered architecture means that each layer
only communicates with the layer directly below it, making the
codebase highly modular, independently testable, and maintainable.
The frontend uses Next.js App Router with route groups to logically
separate authentication flows from dashboard pages without affecting
URL structure. PostgreSQL serves as the primary relational data
store, Redis provides both a high-performance caching layer and
serves as the job queue broker for BullMQ, and Socket.IO enables
bidirectional real-time communication. All services are containerized
and orchestrated through Docker Compose with health checks and
dependency ordering.
KEYWORDS: Repository Pattern, separation of concerns, layered
architecture, modular design, monorepo, App Router, route groups,
bidirectional communication, dependency ordering, containerization

Q4: Why this tech stack?
A: Every technology choice was driven by a specific technical
requirement rather than personal preference. I chose Next.js because
it provides server-side rendering (SSR) for better SEO and initial
load performance, along with file-based routing that keeps the

as a caching layer to reduce expensive Gemini API calls and save
costs, and as a message broker for BullMQ job queues that process
resume analysis asynchronously. Socket.IO was chosen over raw
WebSockets because it provides automatic reconnection with
exponential backoff, room-based broadcasting, and graceful fallback
to HTTP long-polling when WebSocket connections are blocked by
firewalls. PostgreSQL was the natural fit because my data model
(Users, Organizations, Members, Interviews) is inherently
relational with foreign key constraints, joins, and ACID
transaction requirements.
KEYWORDS: type safety, SSR, compile-time error detection,

auto-reconnection, exponential backoff, long-polling fallback,

Q5: Explain the database schema.
A: The database schema consists of four carefully normalized models
designed to enforce data integrity at the database level. The User
model stores authentication credentials with the email field indexed
for fast lookup during login, and passwords are stored as bcrypt
hashes — never as plaintext. The Organization model represents
tenants in the system, with a unique slug field that is indexed for
URL-based organization lookup. The OrganizationMember model serves
as a junction table implementing the many-to-many relationship
between Users and Organizations, with a composite unique constraint
on [userId, organizationId] that prevents duplicate memberships at
the database level, and an enum-based role field (OWNER, ADMIN,
MEMBER) that powers the role-based access control system. The
Interview model tracks interview sessions with a status enum
(PENDING, IN_PROGRESS, COMPLETED), indexed on both organizationId
and status for efficient filtered queries. All models use CUIDs
(Collision-Resistant Unique Identifiers) as primary keys, which are
URL-safe and can be generated client-side without database
coordination. Cascading deletes are configured on all foreign key
relationships to prevent orphaned records — for example, deleting
an Organization automatically removes all associated members and
interviews.
KEYWORDS: data normalization, database integrity, indexed fields,
bcrypt hash, junction table, many-to-many relationship, composite
unique constraint, RBAC, enum types, CUID, cascading deletes,
referential integrity, orphan prevention

Q6: How does authentication work?
A: The authentication system is built on a stateless JWT-based
architecture with bcrypt password hashing, designed to support
horizontal scaling without session storage dependencies.
During registration, the system validates input fields, hashes the
password using bcrypt with a cost factor of 12 rounds (meaning
2^12 = 4,096 hashing iterations, making brute-force attacks
computationally expensive), and persists the user record to
PostgreSQL.
During login, the system retrieves the user by email using an
indexed query, performs a constant-time bcrypt comparison to prevent
timing attacks, and upon successful verification, signs a JWT token
with the userId embedded as the 'sub' (subject) claim and a 7-day
expiration period.
On the frontend, the JWT is stored in Zustand with localStorage
persistence. An Axios request interceptor automatically attaches
the token as a Bearer Authorization header on every outgoing API
request. A response interceptor listens for 401 Unauthorized
responses and triggers automatic logout with state cleanup.
On the backend, a reusable authentication middleware extracts the
Bearer token from the Authorization header, verifies it using
jwt.verify() with the server's secret key, and attaches the decoded
userId to the request object for downstream route handlers.
KEYWORDS: stateless authentication, JWT, bcrypt hashing, cost
factor, timing attack prevention, Bearer token, Axios interceptor,
request/response interceptor, middleware pipeline, horizontal
scaling, token verification, automatic logout

Q7: How does the coding room work?
A: The real-time collaborative coding room is built on Socket.IO's
bidirectional event-driven architecture. When a user joins a room,
the server calls socket.join(roomId) to subscribe that socket to a
specific room channel, and tracks the user's presence in a nested
Map data structure — Map<roomId, Map<socketId, RoomUser>> — which
provides O(1) lookup for user presence and room membership queries.
When a user types code in the Monaco Editor, the onChange event
emits the updated code content to the server, which then broadcasts
it to all OTHER participants in the same room using
socket.to(roomId).emit(), which excludes the sender from receiving
their own update.
The critical engineering challenge was preventing echo loops: when
User B receives a code update and Monaco's onChange handler fires,
it would naively re-emit the same change back to the server,
creating an infinite broadcast loop. I solved this using a useRef
flag called isRemoteChange — the flag is set to true before
applying a remote update, and the onChange handler checks this flag
and skips emitting if it's true. I specifically chose useRef over
useState because useRef mutates synchronously without triggering
React re-renders, which is essential for real-time performance.
On disconnect, the cleanup handler removes the user from the
tracking Map and broadcasts an updated participant list to the
remaining room members.
KEYWORDS: Socket.IO rooms, bidirectional communication, event-driven
architecture, broadcast pattern, echo loop prevention, useRef vs
useState, real-time synchronization, O(1) lookup, Map data
structure, disconnect cleanup, participant tracking

Q8: How does AI question generation work?
A: The AI question generation feature follows a cache-first strategy
combined with structured prompt engineering to deliver fast,
cost-efficient results. When a client requests questions, they send
parameters including the target role and difficulty level. The
service first checks Redis for a cached response using a composite
cache key formatted as "questions:{role}:{difficulty}:{count}",
which ensures granular cache segmentation. On a cache hit, the
cached response is returned immediately without making any external
API call, significantly reducing latency and API costs.
On a cache miss, the service constructs a carefully engineered
prompt that instructs the Gemini AI model to return a structured
JSON response with specific fields for each question. The raw API
response is then parsed as JSON and validated. The parsed questions
are stored in Redis with a 24-hour TTL (Time To Live), balancing
freshness with cost optimization. As a resilience measure, if the
JSON parsing fails (which can happen with AI-generated output), the
system falls back to splitting the raw text response by newline
characters and extracting questions heuristically, ensuring the
user always receives a usable response even when the AI output
format is unexpected.
KEYWORDS: cache-first strategy, prompt engineering, structured
output, composite cache key, cache segmentation, TTL, cache hit/
miss, API cost optimization, JSON parsing, graceful fallback,
resilience, heuristic extraction

Q9: How does resume analysis work?
A: The resume analysis feature implements an asynchronous job
processing pipeline to handle the computationally expensive AI
analysis without blocking the HTTP request-response cycle.
The flow begins when a user uploads a PDF file. Multer middleware
validates the upload (5MB maximum file size, PDF MIME type only)
to prevent abuse. The pdfjs-dist library then extracts raw text
content from the PDF buffer. A unique jobId is generated using
UUID v4 for tracking purposes, and the extracted text along with
metadata is enqueued as a job in the BullMQ "resume-analysis"
queue. The HTTP response returns the jobId immediately to the
client, achieving a non-blocking user experience.
On the worker side, a dedicated BullMQ consumer picks up the job,
sends the resume text to Google Gemini AI with a structured prompt
requesting analysis across multiple dimensions, and stores the
completed result in Redis keyed by the jobId.
The frontend implements a polling mechanism that queries the
/status/:jobId endpoint every 2 seconds. This endpoint checks
Redis for the job result — returning "processing" status if the
job is still in the queue, or the full analysis result once
complete. The result includes an overall score, an ATS
compatibility score, identified strengths, areas of weakness, and
actionable improvement suggestions.
KEYWORDS: asynchronous job processing, non-blocking I/O, producer-
consumer pattern, BullMQ queue, file validation, PDF text
extraction, UUID tracking, polling mechanism, worker process,
structured AI analysis, ATS compatibility scoring

Q10: How does Redis caching work?
A: I implemented a generic, type-safe caching module that follows
the cache-aside pattern and is designed for graceful degradation.
The module exposes three core functions: getCache<T>(key) which
deserializes cached data into typed objects using TypeScript
generics, setCache(key, value, ttl) which serializes and stores
data with a configurable TTL (defaulting to 24 hours), and
deleteCache(key) for manual cache invalidation.
The use of TypeScript generics ensures that cached data maintains
its type information throughout the application — when I retrieve
cached questions, the return type is automatically inferred as the
Question array type, eliminating the need for manual type casting
and reducing runtime errors.
All Redis operations are wrapped in try/catch blocks with error
logging, implementing a fail-open strategy: if Redis is temporarily
unavailable, the application continues functioning by falling back
to direct data fetching rather than crashing. This graceful
degradation ensures that a cache infrastructure failure never
cascades into an application-wide outage.
The caching layer serves two primary use cases: caching AI-generated
questions to reduce expensive Gemini API calls (achieving
approximately 70% cost reduction for repeated queries), and storing
resume analysis job status and results for the polling mechanism.
KEYWORDS: cache-aside pattern, TypeScript generics, type-safe
caching, TTL-based expiration, graceful degradation, fail-open
strategy, cache invalidation, serialization/deserialization, error
isolation, cost optimization, API cost reduction

Q11: How does BullMQ work in your project?
A: BullMQ serves as the distributed job queue system in HireSys,
implementing the producer-consumer pattern backed by Redis for
persistence and reliability. The resume analysis controller acts
as the producer, adding jobs to the "resume-analysis" queue with
the extracted PDF text and metadata as the job payload. A
dedicated worker process acts as the consumer, pulling jobs from
the queue and processing them asynchronously by sending the resume
text to Google Gemini AI for analysis.
The queue is configured with robust failure handling: jobs retry up
to 3 attempts with exponential backoff starting at a 5-second base
delay (so retries occur at approximately 5s, 10s, and 20s
intervals). This backoff strategy prevents overwhelming a
temporarily failing downstream service like the Gemini API. The
queue maintains 100 completed jobs and 50 failed jobs for
observability and debugging purposes.
A critical advantage of using Redis-backed BullMQ is job
persistence — if the server restarts or crashes, all pending and
in-progress jobs survive in Redis and are automatically picked up
when the worker reconnects. The completed analysis results are
stored in Redis cache, which the frontend polling mechanism queries
using the jobId. This entire architecture decouples the
long-running AI processing from the HTTP request lifecycle,
ensuring responsive API endpoints even under heavy analysis load.
KEYWORDS: producer-consumer pattern, distributed job queue,
exponential backoff, job persistence, retry mechanism, failure
handling, asynchronous processing, worker process, job observability,
decoupled architecture, Redis-backed persistence

Q12: How do you handle errors?
A: I implemented a centralized error handling strategy that
provides consistent, secure error responses throughout the entire
application. At the core is a custom AppError class that extends
the native JavaScript Error class, encapsulating both a
human-readable message and an HTTP status code (such as 400 for
bad requests, 404 for not found, or 409 for conflicts).
In the controller layer, all async operations are wrapped in
try/catch blocks. When an error occurs, it is passed to Express's
next(err) function, which forwards it to the centralized error
handling middleware registered at the end of the middleware chain.
The error middleware uses instanceof checking to distinguish
between known AppError instances (which return their specific
status code and message) and unexpected errors (which are logged
internally for debugging but return a generic 500 "Internal server
error" message to the client). This approach ensures that internal
implementation details, stack traces, and sensitive information are
never leaked to end users — a critical security best practice.
For AI-specific operations, I added an additional layer of
resilience with fallback responses, so that even if the Gemini API
returns an unexpected format or fails entirely, the user receives
a meaningful response rather than a cryptic error.
KEYWORDS: centralized error handling, custom error class, AppError,
separation of error concerns, instanceof checking, next(err)
middleware chain, stack trace prevention, information leakage
prevention, fallback responses, defensive programming, HTTP status
codes, error middleware pipeline

Q13: How does multi-tenancy work?
A: The multi-tenancy architecture ensures complete data isolation
between organizations while sharing a single database instance —
a model known as shared-database, separate-schema multi-tenancy.
Each organization is created through a Prisma $transaction that
atomically creates both the Organization record and the first
OrganizationMember record with the OWNER role, ensuring there is
never a state where an organization exists without an owner (which
would be a data integrity violation).
For authorization, every protected endpoint calls an
assertMember(orgId, userId) utility function that queries the
database to verify that the requesting user has an active
membership in the target organization. This implements RBAC
(Role-Based Access Control) at the service level. Data isolation
is enforced through foreign key relationships — all Interview
records are associated with an organizationId, and queries are
always scoped to the current organization context, preventing any
cross-tenant data leakage.
The OrganizationMember junction table supports three roles (OWNER,
ADMIN, MEMBER), allowing fine-grained permission control. The
composite unique constraint on [userId, organizationId] prevents
duplicate memberships at the database level, while cascading
deletes ensure that removing an organization automatically cleans
up all associated members and interviews.
KEYWORDS: multi-tenancy, data isolation, shared database, RBAC,
role-based access control, atomic transactions, $transaction,
assertMember authorization, junction table, composite unique
constraint, cascading deletes, cross-tenant prevention, data
integrity, foreign key scoping

Q14: How do you manage frontend state?

For organization context (which org is currently selected), I use

This layered state architecture — Zustand for global auth, useState

Q15: What security measures did you implement?
A: I implemented a defense-in-depth security strategy with multiple
overlapping layers of protection. Password security uses bcrypt
hashing with 12 salt rounds (2^12 = 4,096 iterations), which is a
one-way hash — not encryption — meaning passwords cannot be
reversed even if the database is compromised. Authentication uses
stateless JWT tokens, eliminating server-side session storage.
Helmet middleware automatically sets critical security headers
including Content-Security-Policy (prevents XSS), X-Frame-Options
(prevents clickjacking), Strict-Transport-Security (enforces
HTTPS), and X-Content-Type-Options (prevents MIME sniffing). CORS
is configured with an explicit origin whitelist, blocking
unauthorized domains from making API requests. All database queries
use Prisma's parameterized queries, which prevent SQL injection by
separating query structure from user-supplied data. Multer file
upload middleware enforces strict validation — 5MB size limit and
PDF-only MIME type filtering. The centralized error handling
middleware prevents stack trace leakage and internal implementation
detail exposure in error responses.
I am aware of a known security gap: storing JWT tokens in
localStorage makes them vulnerable to XSS attacks. In a production
hardening phase, I would migrate to HttpOnly cookies with
SameSite=Strict and implement CSRF token protection to address this
vulnerability.
KEYWORDS: defense-in-depth, bcrypt hashing, salt rounds, one-way
hash, stateless JWT, Helmet security headers, Content-Security-
Policy, clickjacking prevention, HSTS, CORS origin whitelist,
parameterized queries, SQL injection prevention, file upload
validation, stack trace prevention, XSS awareness, HttpOnly
cookies, CSRF protection, MIME sniffing prevention

Q17: What if the database crashes?
A: My system is designed with multiple layers of resilience and
recovery for database failure scenarios. For immediate detection,
Docker Compose health checks use pg_isready to monitor PostgreSQL
availability, and restart policies (restart: unless-stopped)
automatically restart the container on failure.
For prevention, I would implement automated pg_dump backup
schedules (daily full backups with WAL archiving for point-in-time

For recovery, the process depends on the failure severity: a

rather than failing completely: Redis continues serving cached AI
responses, so users can still access previously generated questions.
BullMQ jobs waiting in the queue are persisted in Redis and will
automatically retry processing once the database recovers, ensuring
no data loss in the job pipeline.

Q19: Biggest challenge you faced?
A: The most significant engineering challenge was debugging and
solving a real-time echo loop in the collaborative coding room.
The problem manifested when User A typed code and the change was
broadcast to User B via Socket.IO. When User B's Monaco Editor
received the update and applied it, Monaco's onChange event handler
fired automatically, which sent the same code change back to the
server, which broadcast it back to User A, creating an infinite
feedback loop that caused the editor to freeze and the network
to saturate with redundant messages.
I solved this by implementing a synchronization flag using React's
useRef hook. Before applying a remotely received code update, the
isRemoteChange ref is set to true. The onChange handler checks this
flag at the very start of its execution — if isRemoteChange is
true, it skips the emit and resets the flag. The critical design
decision was choosing useRef over useState: useRef updates are
synchronous and do not trigger React re-renders, which is essential
because the flag needs to be set and checked within the same
synchronous execution frame. Using useState would introduce an
asynchronous state update that could result in the flag being
checked before it's actually set, reintroducing the echo loop.
This experience taught me the importance of understanding React's
rendering lifecycle and the distinction between synchronous and
asynchronous state management in real-time applications.
KEYWORDS: echo loop, infinite feedback loop, real-time debugging,
useRef vs useState, synchronous flag, rendering lifecycle,
synchronization mechanism, Socket.IO broadcast, Monaco Editor,
event handler optimization, asynchronous state pitfall

Q20: What trade-offs did you make?
A: I made several deliberate, pragmatic engineering trade-offs that
prioritize simplicity and development velocity for the current
scale while acknowledging the path to more robust solutions.
First, I chose last-write-wins concurrency over CRDT (Conflict-free
Replicated Data Types like Yjs). For the current 1-2 user coding
sessions, last-write-wins is simple and effective; CRDT adds
significant complexity that would be warranted only at larger
concurrent user counts.
Second, I chose HTTP polling for resume analysis status over
WebSocket push. Since resume analysis is an infrequent operation
(once per user per session), the overhead of polling every 2 seconds
is negligible, and it's significantly simpler to implement and debug
than managing WebSocket channels for one-off status updates.
Third, I stored JWT tokens in localStorage instead of HttpOnly
cookies. This simplifies the frontend architecture (no CSRF token
management needed) but introduces XSS vulnerability — a trade-off
I acknowledge and would address in production hardening.
Fourth, I track connected socket users in an in-memory Map rather
than Redis Pub/Sub. This works correctly for a single-server
deployment but would need migration to Redis adapter for
multi-server horizontal scaling.
Each trade-off represents a conscious decision where I understood
both alternatives and chose the one appropriate for the current
requirements.
KEYWORDS: engineering trade-offs, pragmatic decision-making,
last-write-wins vs CRDT, polling vs push, localStorage vs HttpOnly
cookies, in-memory vs distributed state, simplicity vs correctness,
technical debt awareness, horizontal scaling readiness

Q21: What is the Repository Pattern?
A: The Repository Pattern is a structural design pattern that
abstracts the data access layer into its own dedicated class or
module, creating a clean separation between business logic and
database operations. In HireSys, I implement this as a four-layer
architecture: Routes define API endpoints and attach middleware,
Controllers parse HTTP requests and format responses (handling the
transport layer), Services contain all business logic, validation,
and orchestration (handling the domain layer), and Repositories
encapsulate all database queries using Prisma ORM (handling the
persistence layer).
The primary benefits are threefold. First, testability: I can write
unit tests for services by mocking the repository layer with test
doubles, completely eliminating the need for a real database during
testing. Second, maintainability: each layer follows the Single
Responsibility Principle — if I need to change how data is queried,
I only modify the repository; business logic in services remains
untouched. Third, flexibility: if the team decides to migrate from
Prisma to TypeORM or raw SQL, only the repository layer needs
modification — services, controllers, and routes are completely
unaffected because they depend on the repository abstraction, not
the ORM implementation directly. This aligns with the Dependency
Inversion Principle from SOLID: high-level modules (services)
depend on abstractions (repository interface), not low-level
details (Prisma client).
KEYWORDS: Repository Pattern, data access abstraction, separation
of concerns, layered architecture, Single Responsibility Principle,
Dependency Inversion Principle, SOLID, testability, test doubles,
mock repository, ORM-agnostic design, domain layer, persistence
layer, transport layer

Q22: How does Docker Compose work in your project?
A: Docker Compose orchestrates the entire multi-service application
stack through a declarative YAML configuration that defines four

The PostgreSQL service (postgres:16-alpine) runs with a health

environment key in the compose file, keeping secrets out of the
codebase.

Q23: How would you add video calling?
A: I would implement video calling using WebRTC (Web Real-Time
Communication) for peer-to-peer media streaming, leveraging the
existing Socket.IO infrastructure as the signaling channel.
The flow would work as follows: when a user initiates a video call,
the browser captures the local media stream using
navigator.mediaDevices.getUserMedia(). Socket.IO handles the
signaling phase — exchanging SDP (Session Description Protocol)
offers and answers between peers to negotiate codec and media
capabilities, and relaying ICE (Interactive Connectivity
Establishment) candidates to discover the optimal network path
between peers.
For NAT traversal (allowing peers behind routers and firewalls to
connect), I would configure STUN (Session Traversal Utilities for
NAT) servers to discover public IP addresses, and TURN (Traversal
Using Relays around NAT) servers as a relay fallback when direct
peer-to-peer connection is not possible due to restrictive
firewalls.
For group calls with more than 2 participants, direct peer-to-peer
mesh networking becomes bandwidth-intensive (each peer sends N-1
streams). I would implement an SFU (Selective Forwarding Unit)
architecture using a library like MediaSoup, where each participant
sends one stream to the server, and the server selectively forwards
appropriate streams to each participant. For faster time-to-market,
managed services like Twilio Video or Daily.co provide SDKs that
abstract this complexity.
KEYWORDS: WebRTC, peer-to-peer, SDP signaling, ICE candidates,
NAT traversal, STUN server, TURN relay, getUserMedia, media stream,
SFU, Selective Forwarding Unit, MediaSoup, mesh networking, Twilio,
codec negotiation, signaling channel

Q24: How would you test this project?
A: I would implement a comprehensive testing strategy organized
into four tiers, following the testing pyramid principle of having
more unit tests than integration tests, and more integration tests
than end-to-end tests.
Unit Tests with Jest: Test individual services and repositories
in isolation by mocking dependencies. The Repository Pattern makes
this natural — I can swap the real Prisma repository with a mock
that returns predefined data, testing business logic without any
database or network dependency.
Integration Tests with Supertest: Test API endpoints end-to-end
within the backend by making actual HTTP requests to Express routes,
verifying request validation, middleware execution, correct status
codes, and response body structure.
Component Tests with React Testing Library (RTL): Test React
components by rendering them in a simulated DOM environment and
verifying user interactions, state changes, and rendered output.
RTL encourages testing from the user's perspective (clicking
buttons, filling forms) rather than testing implementation details.
End-to-End Tests with Playwright: Test complete user flows across
the entire application stack — logging in, creating organizations,
joining coding rooms, and verifying real-time collaboration —
running in real browser instances to catch integration issues that
lower-level tests might miss.
KEYWORDS: testing pyramid, unit testing, Jest, mock dependencies,
test doubles, integration testing, Supertest, API endpoint testing,
component testing, React Testing Library, end-to-end testing,
Playwright, browser automation, test isolation, testing strategy

Q25: What would you do differently?
A: Looking back with the experience gained from building HireSys,
there are five specific improvements I would prioritize if starting
over, while keeping the core architectural decisions that proved
effective.
First, I would store JWT tokens in HttpOnly cookies instead of
localStorage, adding SameSite=Strict attribute and CSRF token
validation to eliminate the XSS vulnerability — this is the most
critical security improvement.
Second, I would implement Zod schema validation on both frontend
and backend, creating shared validation schemas in the monorepo's
packages directory. This provides runtime type safety at API
boundaries with descriptive error messages, catching malformed
data before it reaches the service layer.
Third, I would leverage Next.js Server Components for data fetching
pages, reducing client-side JavaScript bundle size and eliminating
loading spinner states by streaming HTML with data already rendered.
Fourth, I would implement WebSocket authentication on the initial
connection handshake using the auth option in Socket.IO client,
rather than relying solely on HTTP middleware. This prevents
unauthorized users from establishing Socket.IO connections in the
first place.
Fifth, I would add rate limiting from day one using Redis-backed
sliding window counters on all AI endpoints, preventing abuse and
controlling API costs proactively rather than reactively.
The core architectural decisions — Repository Pattern, BullMQ for
async processing, Redis caching, Docker containerization — were
validated through development and I would make the same choices
again.
KEYWORDS: self-awareness, continuous improvement, HttpOnly cookies,
CSRF protection, Zod validation, shared schemas, Server Components,
streaming SSR, WebSocket authentication, connection handshake,
rate limiting, sliding window algorithm, validated architecture,
iterative refinement

REACT (Top 10)
────────────────────────────────────────────────

1. What is Virtual DOM?
→ JS representation of real DOM. React diffs old vs new virtual
  tree, updates only changed parts. Faster than direct DOM
  manipulation.

2. useState vs useRef?
→ useState triggers re-render on change. useRef persists value
  without re-render. Use useRef for DOM refs, flags, intervals.

3. What is useEffect cleanup?
→ Function returned from useEffect. Runs on unmount and before
  re-run. Used to clear timers, remove listeners, disconnect
  sockets.

4. useCallback vs useMemo?
→ useCallback memoizes a FUNCTION reference. useMemo memoizes
  a computed VALUE. Both recalculate only when dependencies
  change.

5. What is lifting state up?
→ Moving state to the nearest common parent so sibling
  components can share it via props.

6. Controlled vs Uncontrolled components?
→ Controlled: value managed by React state (value + onChange).
  Uncontrolled: value managed by DOM (ref to access value).

7. What is React.memo?
→ HOC that skips re-render if props haven't changed. Used for
  performance optimization on expensive child components.

8. What is the key prop in lists?
→ Unique identifier that helps React track which items changed,
  added, or removed. Never use array index as key if list can
  reorder.

9. What is Context API?
→ Way to share data across components without prop drilling.
  Create context → Provider wraps tree → useContext consumes.

10. What are fragments?
→ <></> groups multiple elements without adding extra DOM node.
   Needed because components must return single root element.

DBMS (Top 10)
────────────────────────────────────────────────

1. What is ACID?
→ Atomicity (all or nothing), Consistency (valid state after
  transaction), Isolation (concurrent txns don't interfere),
  Durability (committed data persists even on crash).

2. What is normalization?
→ Reducing redundancy by splitting into related tables.
  1NF: atomic values. 2NF: no partial dependencies.
  3NF: no transitive dependencies.

3. What is indexing?
→ B-tree data structure for fast lookups. Trade-off: faster
  reads, slower writes, more storage. I index email, slug,
  orgId, status.

4. What is a foreign key?
→ Column that references primary key of another table.
  Enforces referential integrity. onDelete: Cascade removes
  children when parent is deleted.

5. What is a transaction?
→ Group of operations that all succeed or all fail. I use
  Prisma $transaction to create org + owner member atomically.

6. What is a primary key?
→ Unique identifier for each row. Cannot be NULL. I use
  CUID (collision-resistant unique ID) generated by Prisma.

7. SQL vs NoSQL?
→ SQL: structured schema, ACID, joins. Best for relational data.
  NoSQL: flexible schema, horizontal scaling. Best for documents.
  I chose SQL because User→Org→Interview is relational.

8. What is a junction/join table?
→ Table that implements many-to-many relationship. My
  OrganizationMember links Users and Organizations with
  additional role column.

9. What is a composite key?
→ Unique constraint on multiple columns. My OrganizationMember
  has @@unique([userId, organizationId]) — prevents duplicate
  memberships.

10. What is an ORM?
→ Object-Relational Mapping — maps code objects to database
   tables. Prisma generates TypeScript types from schema,
   provides type-safe queries and auto migrations.

1. Four pillars of OOP?
→ Encapsulation (bundle data+methods), Abstraction (hide
  complexity), Inheritance (extend classes), Polymorphism
  (same interface, different behavior).

2. What is encapsulation?
→ Bundling data and methods, hiding internal details. My

3. What is abstraction?

4. What is inheritance?

5. What is polymorphism?

  middleware handles AppError (specific status) and generic
  Error (500) differently using instanceof check.

6. What is SOLID?
→ S: Single Responsibility (each module = one feature).
  O: Open/Closed (extend, don't modify). L: Liskov Substitution.
  I: Interface Segregation. D: Dependency Inversion (depend on
  abstractions like Repository, not Prisma directly).

7. What is a class vs object?
→ Class is a blueprint/template. Object is an instance.
  AuthService is the class, new AuthService() creates an object.

8. What is a constructor?
→ Method called when creating an object. My AppError constructor
  takes message and statusCode, calls super(message).

9. What is method overriding?
→ Child class redefines parent's method. Not explicitly in my
  code but AppError's constructor overrides Error's behavior.

10. Difference between interface and abstract class?
→ Interface: only method signatures, no implementation, multiple
   inheritance. Abstract class: can have implementations, single
   inheritance. TypeScript uses interfaces heavily.

SQL (Top 10)
────────────────────────────────────────────────

1. What is SELECT?
→ Retrieves data. SELECT * FROM users WHERE email = 'x@y.com';

2. What are JOINs?
→ Combine rows from multiple tables. INNER JOIN: only matches.
  LEFT JOIN: all left + matching right. RIGHT JOIN: opposite.

3. What is GROUP BY?
→ Groups rows for aggregation. SELECT status, COUNT(*) FROM
  interviews GROUP BY status;

4. What is WHERE vs HAVING?
→ WHERE filters rows before grouping. HAVING filters groups
  after GROUP BY.

5. What is ORDER BY?
→ Sorts results. ORDER BY createdAt DESC returns newest first.
  ASC for ascending (default).

6. INSERT, UPDATE, DELETE?
→ INSERT INTO users (name, email) VALUES ('Lucky', 'x@y.com');
  UPDATE users SET name = 'New' WHERE id = '1';
  DELETE FROM users WHERE id = '1';

7. What is DISTINCT?
→ Returns unique values only. SELECT DISTINCT status FROM
  interviews;

8. What are aggregate functions?
→ COUNT, SUM, AVG, MIN, MAX. Operate on groups of rows.
  SELECT COUNT(*) FROM users;

9. What is a subquery?
→ Query inside another query. SELECT * FROM users WHERE id IN
  (SELECT userId FROM org_members WHERE orgId = 'x');

10. What is LIKE?
→ Pattern matching. WHERE name LIKE '%Lucky%' matches any
   string containing "Lucky". % = wildcard.
